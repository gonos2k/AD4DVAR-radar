## Required operands, checked one by one

1. **Three actual input observations.** A case needs three same-grid dBZ arrays with shape `[3,H,W]`; the public contract validates exactly that shape (`src/advar/cli.py:432-440`, `src/advar/nowcast.py:9845-9885`). The three canonical UTC times must be separated by the configured 10-minute interval (`src/advar/nowcast.py:288-290`, `README.md:339-344`). No such arrays or times are present. The RADAR scripts produce `np_velo`/`vr` radial velocity in m/s (`radar1.py:158-168`, `aa1.py:78-88`), which cannot be passed as ADVAR reflectivity without a physically specified conversion.

2. **Independent future target truth.** A comparison needs future observed reflectivity on the same domain, with a target valid mask and source/QC identity. `VerificationBundle` requires floating `[lead,H,W]` frames, a same-shaped boolean mask, finite values on valid cells, increasing canonical UTC `valid_times`, and SHA-256 grid/product/QC identities (`src/advar/sensitivity.py:7441-7510`). No future observations, target masks, or target product files are available. With the default 10-minute/180-minute forecast, `_resolve_verification()` expects the lead times from +10 through +180 minutes (`src/advar/sensitivity.py:11720-11737`), i.e. 18 target frames unless a documented forecast horizon is changed consistently.

3. **One fixed physical evaluation domain.** The input and target must share the forecast grid contract digest. The current scientific path requires the v6 projected-grid identity, geometry, shape, current metric-domain evidence, and matching projected-grid identity (`src/advar/sensitivity.py:11627-11661`; `src/advar/nowcast.py:2873-2889`). The documented example uses EPSG:5179, 1,000 m spacing, and an explicit affine/cell convention (`README.md:315-347`). None of the available scripts or images carries a canonical grid hash, projected origin, affine, CRS digest, shape contract, or fixed evaluation mask. The packaged EPSG-5179 evidence JSON is static domain evidence, not a case grid identity or data mask.

4. **Availability and QC masks.** The case must preserve the three time-dependent input masks and the target mask on the full fixed domain. The CLI only accepts a boolean input mask with exactly `[3,H,W]` (`src/advar/cli.py:247-250,432-440`), while the current verification bundle also requires quality/error tensors for current observation-error contracts (`src/advar/sensitivity.py:7547-7647`). There is no QC mask, quality-weight field, source assignment map, outage map, attenuation/beam-blockage evidence, or target valid mask in the available paths.

5. **P0 configuration and diagnostics.** A fair P0 arm must record the actual `NowcastConfig`, physical motion limit, pair selection/count/conflict, coverage, support, confidence, and background usage. The defaults include 10-minute cadence, 180-minute horizon, dBZ bounds, echo threshold, pair/PSR gates, and publish support (`src/advar/nowcast.py:288-331`). P0 metadata stores `tendency_source`, motion/growth pair selection and counts, conflicts, coverage, and background provenance (`src/advar/nowcast.py:4383-4428`). No case-specific P0 config or output artifact exists. Using code defaults would be a research invocation, not a calibrated actual-radar comparison.

6. **P1 configuration and selection diagnostics.** A P1 arm needs the actual observation standard deviation, quality weights/QC, analysis config, and any background or prior artifact. P1 acceptance must report `outer_converged`, `final_linearization_stationary`, `final_robust_stationary`, `final_irls_fixed_point`, `p1_forecast_eligible`, `posterior_eligible`, and `fso_eligible` (`src/advar/variational.py:3434-3530`; exported by `src/advar/cli.py:1147-1169`). The final diagnostics also include robust/stationarity gradients, IRLS weight change, reachability, unresolved amplitude, quality support, and fallback/degraded reason (`src/advar/cli.py:1170-1280`). No P1 input, analysis artifact, prior application, or configured values are available. Operational P0/P1 additionally requires a calibration manifest, its approved digest, complete data identity, and all calibrated values (`src/advar/cli.py:365-399,805-818`); none exists in the documented paths.

7. **Paired A/B arm identity.** Candidate and parent must consume the same three frames, QC/source maps, background, grid/time contract, fixed domain/mask, target, and scoring configuration. The only allowed experimental difference must be a predeclared candidate/parent model or prior/config change. The run artifact records input and forecast identities and P1 analysis input identity (`README.md:353-383`). There are no two forecast-run artifacts, parent/candidate identifiers, or model/prior pair to compare. The acceptance verifier’s stage JSON cannot substitute for paired forecasts: it reports `semantic_e2e_validated=False` and `eligible_for_scientific_review=False` for generic stage artifacts (`README.md:1398-1408`; `src/advar/acceptance.py:395-430`).

8. **Learning policy, FSOI, and rejection reasons.** Automatic learning requires a current typed verification bundle, an approved `AutomatedLearningPolicy`, root-owned approved policy trust store, physical-radar perturbation, accepted P1 linearization, and candidate ranking/validation artifacts. The policy enforces physical metrics, full-map leads, active-set/feasibility/Gauss–Newton/baseline gates, and strict budgets (`src/advar/sensitivity.py:9763-9907`; `README.md:1582-1602`). The learning API is a Python API, not part of the CLI (`src/advar/sensitivity.py:13885-13946`). Its typed `LearningEligibility` records `eligible`, `reasons`, and `policy_digest` (`src/advar/sensitivity.py:10287-10302`); rejection reasons include unapproved policy, missing/invalid physical perturbation, missing or unapproved linearization/runtime, uncertified baseline branch, operation/PCG/wall budgets, no material signal, and failed first-order validation (`src/advar/sensitivity.py:13901-14086`). No policy JSON, trust store, perturbation, FSO/FSOI, linearization, or candidate/parent learning evidence is available, so no learning rejection diagnostic can be honestly emitted for a case.

9. **Observation-error and source provenance.** A current v22 verification bundle also needs the measurement lineage (mask/censor/floor policy and quantization), quality and observation-standard-deviation tensors, source map, detection limit, acquisition offset/age, spatial metric mask, typed observation-error contract, and replayable derivation artifact (`src/advar/sensitivity.py:7450-7466,7511-7545,7547-7647`; current bundle identity is registered in `src/advar/_contract_registry.py:155-159`). The available scripts and PNGs have none of these source/product/QC/calibration digests.

10. **Evaluation records.** The report must state the fixed domain, target leads, evaluated and missing pixel fractions, P0/P1 arm selection, and every learning rejection reason. The checklist calls these out directly (`THIRD_CODE_REVIEW_CHECKLIST.md:40-43`). Without the target mask and fixed-domain identity, evaluated/missing fractions cannot be measured; dropping cells independently per arm would invalidate the A/B comparison.
