# f462 inexact continuation — RED contract audit

Date: 2026-10-07
Scope: read-only audit of the inexact continuation wrapper, committed-base loader, continuation bookkeeping, and the archived PR #255 comparison receipt. No FV, HVP, PCG, forecast, adjoint, reanalysis, or tests were run. No production source was edited.

## Decision

The numerical core can support the proposed bounded continuation: `dual_merit_continuation` accepts `linear_mode="inexact"`, at most three iterations, a 90-HVP cap, a 720-second cooperative deadline, a 780-second guarded wall limit, a 1 GiB RSS cap, and one guarded launch. A new invocation with no `shared_counts` starts its HVP and PCG accounting at zero. Its forcing tolerance is recomputed from each current point's full gradient infinity norm. This supports a new, explicitly pinned inexact plan from f462 without changing the PR #255 comparison retrospectively.

**The current wrapper has a blocking source-receipt mismatch and does not yet enforce selected-arm provenance. Do not launch it in its current state.**

## Blocking findings

1. **The declared base path has no required sidecars.** `fv_point_3h_inexact_continuation.py:14` declares the selected arm file `d31_inexact_comparison_20261007_attempt1/inexact.json`. But `committed_base.base_path()` requires the base JSON plus adjacent `.run.json` and `.resource.json` receipts (`fv_point_3h_committed_base.py:32-54`). The comparison directory contains `step.json`, `step.run.json`, and `step.resource.json`, plus `inexact.json`; it does not contain `inexact.run.json` or `inexact.resource.json`. Therefore the wrapper's call through `committed.load_base()` fails before an FV evaluation.

   **Reproduction:** `ls -la graphify-out/fv-root-cause-20260919/d31_inexact_comparison_20261007_attempt1` shows the three `step.*` receipts and only `inexact.json`; the selected-arm sidecar paths derived from `inexact.json` are absent.

   **Required resolution:** pin the comparison top-level `step.json` and its parent/resource sidecars as the base receipt. The wrapper must then independently close `arms.inexact` against the top-level selected endpoint before passing the verified start to the common continuation. Preserve the selected arm file hash as an additional archive pin if it is used as endpoint evidence. Do not invent arm-level resource receipts.

2. **The wrapper does not prove that the endpoint came from the selected inexact arm.** `_validated_loader()` delegates to `committed.load_base()` and compares only accepted-control hash, base-control hash, parameter hash, and frozen-input digest (`fv_point_3h_inexact_continuation.py:25-43`). The shared `_accepted_endpoint()` checks generic accepted-trial and endpoint closure, but it cannot establish which comparison arm supplied the value (`fv_point_3h_committed_base.py:116-162`). A plan-pinned comparison must also require `comparison_complete is True`, `selected_arm == planned_selected_arm == "inexact"`, normal completion, and one accepted inexact step; then compare the `arms.inexact` control/hash, J, Phi, gradient, branch, input/runtime/source status to the top-level selected endpoint. The strict arm is audit context and must never provide a fallback start.

   **Why this matters:** `inexact.json` and `strict.json` are both normally completed one-step endpoints from the same d31 base. Generic endpoint validity alone does not distinguish f462 from the strict endpoint `e986…`.

## Counter and policy contract

The archived comparison top-level receipt reports `hvp_calls=53` and `pcg_iterations_completed=49` because it aggregates both arms. The selected inexact arm also carries those shared totals; its own solve cost is `new_hvp_calls=22`, with the comparison's `arm_counter_deltas.inexact` recording 22 HVP, 20 PCG iterations, and one solve. These values were confirmed by reading the saved JSON; no solver was rerun.

The next continuation must start fresh counters at zero. `dual_merit_continuation.run()` and `run_iterations()` initialize the counter keys to zero when `shared_counts` is omitted (`fv_point_3h_dual_merit_continuation.py:235-243, 576-583`). Do not pass the comparison's top-level or arm cumulative counters as `shared_counts`; that would incorrectly spend 53 of the new launch's 90 HVP allowance before the first current-point product. Keep the old comparison totals in provenance fields only. The 90-HVP counter must continue to include both PCG products and the independently recomputed true-residual Hs.

The executed policy should be pinned as `policy_dict("inexact", 3)` with `linear_mode="inexact"`, at most 3 iterations, 90 HVP, PCG maximum 40, internal 720 seconds, outer 780 seconds, sampled RSS at most 1 GiB, and one launch (`fv_point_3h_dual_merit_continuation.py:35-38, 50-74`). Each solve recomputes `eta=clip(0.1*||g||∞,[1e-10,1e-3])` at the current point (`:78-84, 286-301`). f462 starts at `||g||∞≈0.416619`, so the first solve uses the 1e-3 ceiling. The plan must not claim the tightening zone `||g||∞<1e-2` will be reached; record whether it occurs and the actual eta per solve.

No automatic J-only fallback or changed prior/tolerance is needed. The core direction gate refuses when the inexact direction fails resolved J/Phi descent and curvature checks; dual merit search retains both actual Armijo gates. Root eligibility remains `||g||∞<=1e-10` with fresh re-evaluation (`fv_point_3h_dual_merit_continuation.py:281-301, 315 onward`). A three-iteration limit or budget refusal remains a completed bounded search receipt, not a stationary-point claim.

## Stop, budget, and provenance handling

- Cooperative HVP/deadline refusal is recorded as a numerical `budget_refusal`; a numerical refusal can still have process execution status `completed` (`fv_point_3h_dual_merit_continuation.py:435-459`). Preserve this distinction in the parent summary.
- External wall/RSS termination is classified separately by `execution_status()` and must preserve the child partial receipt; it must not be relaunched or converted into a completed numerical endpoint (`:90-112, 750-781`).
- `run_iterations()` already checkpoints the committed control and current iteration after progress updates; a partial PCG solve records HVP calls at refusal and explicitly marks failed-solve PCG iterations as `not_recorded` (`:259-304, 435-458`). Do not infer PCG iterations from HVP deltas.
- On each accepted point, the next loop recomputes fresh J, full gradient, strict branch/margins and a new current-point HVP direction; no prior direction is reused (`:268-304`). The cached f82c matrix remains only the preconditioner, as stated in the policy and run metadata.

## Minimal regression evidence needed before launch

1. A loader-level fixture that uses the actual comparison `step.json`/parent/resource structure and proves that only a fully completed `selected_arm=inexact` receipt yields f462.
2. Mutations showing rejection when `selected_arm` is null/strict, `comparison_complete` is false, the selected arm hash or J/Phi/gradient/branch differs from the top endpoint, or an accepted endpoint exists under a budget-refused parent.
3. A counter fixture proving a fresh continuation starts with zero counters even though its source comparison says 53 HVP / 49 PCG, and separately preserves the old `22 HVP / 20 PCG` inexact arm delta as provenance.
4. A policy fixture pinning `policy_dict("inexact", 3)`, the 90/720/780/1-GiB/one-launch limits, unchanged final root threshold, and per-iteration eta recomputation. No test should assert that this run reaches eta below 1e-3 or reaches a root.

The present new test file does not cover these points: its `_case()` monkeypatches `committed.load_base` and `committed.base_path` (`tests/test_fv_point_3h_inexact_continuation.py:17-46`), so it cannot detect the absent arm sidecars; it also validates a raw arm directly without a selected-arm comparison wrapper (`:49-75`).
