## Findings

### P1 — A supported PCG numerical refusal is not classified; durable report remains pre-solve

`examples/weather_scenarios/fv_point_3h_schur_newton_step.py:92-96` translates only five exact `RuntimeError` messages from `matrix_free.pcg` into `StepRefusal`. The shared solver also raises `RuntimeError("PCG direction update is not finite")` at `src/advar/matrix_free.py:502`. If this finite-arithmetic guard fires, it escapes the new caller’s `except` clauses (`fv_point_3h_hvp_newton_step.py:269-279`). The child exits with an error instead of writing a terminal numerical refusal report.

There is a related report durability defect for any unexpected PCG/program exception: the `finally` block at `fv_point_3h_hvp_newton_step.py:210-214` copies actual HVP counts into the in-memory record, but only the pre-PCG record was written at line 196. Since the exception propagates before line 289, `step.json` falsely remains `phase=linear_solve`, `numerical_status=not_reached`, and both HVP counters zero.

Toy reproduction: monkeypatch `solve_newton_direction` to call its supplied wrapped HVP once, then raise `RuntimeError("synthetic kernel failure")`. `run()` propagates the error; the durable JSON reports `linear_solve/not_reached/0 started/0 completed` despite one product being started and completed. The mock uses the pinned plan/archive inputs and a quadratic toy objective; no FV trajectory or HVP was evaluated. Classify the shared PCG direction-update message as a numerical refusal. For genuinely unexpected errors, retain propagation/traceback while durably writing a terminal failure record with the counts and error class/message before re-raising.

### P2 — Post-accept work can cross the internal deadline without a final refusal gate

The accepted candidate is guarded after the search and after each physical-state calculation (`fv_point_3h_hvp_newton_step.py:232-254`). However, `diagnostics.model_diagnostics(...)` runs after the last deadline check and is included in the accepted `record.update` (`255-267`); no check follows it before committing `optimizer_steps_applied=1`. The final source hash/input-integrity work (`280-289`) also has no deadline check before the finished report is written. If either post-accept operation crosses the 240-second cooperative deadline, the result can still claim an accepted optimizer step after its configured internal budget. Preserve the accepted candidate only if the deadline remains valid after diagnostics and final integrity checks; otherwise serialize it as uncommitted/budget-refused. The observed run completed in 217.91 child seconds (219.13 outer seconds), so this edge was not exercised in the actual result.
