## Writer requirements and concrete failure cases

Current `_write` in `examples/weather_scenarios/fv_point_3h_tangent_continuation.py:565` builds the entire `json.dumps(..., indent=2)` string, then writes a PID-named temporary file and replaces the target. The streaming replacement must preserve byte-for-byte JSON output for valid records: sorted keys, two-space indentation, `allow_nan=False`, default text encoding, and one trailing newline. Stream `JSONEncoder.iterencode` chunks to the temporary file; do not first concatenate chunks into a whole serialized string.

A streamed encoding can fail after writing a prefix (for example, a late nested NaN/Infinity with `allow_nan=False`), and filesystem writes or `os.replace` can fail. In each such case, preserve the prior target bytes and remove only the temporary path. On success, the new target must remain present and parseable. Cleanup must be scoped to the temp path: after `os.replace(temp, path)`, the temp name no longer exists, while `path` is the newly committed file; generic cleanup against `path` would delete the fresh checkpoint. Check these concrete cases with tiny filesystem tests: a successful same-byte replacement; late nested NaN/Infinity; injected mid-stream write failure; and injected replace failure. For each failure, assert old target bytes remain unchanged and no temp file remains; after success, assert the target exists and matches the legacy serialization bytes.

## Progress retirement at commit

`direction_progress` stores the in-flight comparison under `record["comparison_progress"]` (`continuation.py:1031`); `committed_progress` copies the now-accepted iteration and current/last-confirmed control/theta into the record, then writes it (`:1014–1028`). This leaves a second serialized copy of the accepted model comparisons in the checkpoint; the interrupted receipt measures the duplicate at about 29.37 MB beside about 61.46 MB in `iterations`.

Retire progress only as part of the same atomic commit checkpoint that stores the accepted iteration and its current/last-confirmed state. Build a commit snapshot without `comparison_progress`, atomically write that snapshot, and remove the in-memory progress key only after `_write` succeeds. If writing fails, keep the in-memory progress and the on-disk pre-commit checkpoint intact. Never pop progress first and then rely on a subsequent write: that can lose the only in-flight record if serialization/replacement fails. This rule keeps pre-commit progress available after refusal/interruption and removes only progress made redundant by a durably installed commit record.
